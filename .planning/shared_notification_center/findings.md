# Findings

- Existing customer notification page loads `GET /notifications`, marks one with `PATCH /notifications/:id/read`, and marks all with `PATCH /notifications/read-all`.
- Backend list query already returns every notification type and orders by `created_at DESC`, so the popup can safely show all types newest-first. A frontend fallback label/presentation is still needed for future unknown types.
- `GET /notifications/unread-count` exists, but loading the full list is necessary for the popup and provides the badge count without a second initial request.
- Backend currently has no mark-unread or clear-all endpoint. The requested read/unread toggle and delete-all behavior require small authenticated endpoints scoped by `user_id`.
- Existing full notification page contains its own type metadata and related-entity routing, but uses emoji icons. Shared popup utilities should use Lucide icons and generic fallback behavior while the full page remains the detail destination.
- CustomerLayout covers Profile, Agent, and normal customer pages through `Navbar`; Home and AdminHeader are the other two account-action entry points. Replacing `UserAccountMenu` with one `AccountActions` cluster in these three places gives complete coverage.
- No existing frontend tests mock the notification API, so the new popup needs a focused self-contained mock for `api.get/patch/delete`.
- Integration search confirms all three header entry points now use `AccountActions`; the only obsolete bell implementation left is the old `.home-bell-btn` CSS block.
- Backend formatting resolves the CRLF lint noise. The only remaining lint errors are in an existing transaction test mock typed as `any`; replacing it with a typed callback removes both `require-await` and unsafe-call errors without altering production code.
- Final integration search finds only the intentional `UserAccountMenu` child inside `AccountActions`; there are no legacy Home bell or initials-avatar integrations. Diff check is clean aside from informational Windows line-ending warnings.
- Both notification builds succeed. Frontend produces only its existing large-chunk advisory, unrelated to this feature.
- Runtime configuration uses `VITE_API_URL=http://localhost:5000/api`. The hidden backend launch succeeded on port 5000; the later foreground diagnostic failed with `EADDRINUSE` only because that new dev server was already listening. An unauthenticated notification request returns the expected 401, confirming route availability and auth protection.
- Real notification producers are split across modules: reservations and cemetery-services insert notification rows directly with SQL, while contracts and reminders call `NotificationsService`. The popup must continue consuming the canonical `GET /notifications` response rather than maintaining a separate mock/type-specific feed.
- The canonical list endpoint returns `id`, `type`, `title`, `message`, `isRead`, `relatedEntityType`, `relatedEntityId`, and `createdAt`, filtered by the authenticated user and ordered by `created_at DESC`. Popup actions match the authenticated read/unread/read-all/delete endpoints exactly.
- A one-second polling loop is the smallest change that meets the requested maximum one-second delay without introducing a new transport. Both popup and full notification page now use it; an in-flight guard prevents overlapping GET requests and a mutation version prevents stale GET responses from overwriting optimistic read/clear actions. The list endpoint is marked `Cache-Control: no-store`.
- Authenticated runtime verification against the live server returned HTTP 200, one real admin notification, `Cache-Control: no-store`, and the exact expected fields. The newest real row was `request_submitted`; no preview code remains.
