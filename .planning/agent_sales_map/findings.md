# Findings

- The screenshot shows raw `mapX/mapY` coordinates exposed to the customer and speculative language about where the gate might be.
- The opened map card uses small labels/values and surfaces only area, direction, size, and price.
- Comparison-selection feedback appears awkward after the compare action and needs tracing before editing.
- Plot recommendation payloads intentionally include `mapX/mapY` for rendering; the prompt currently teaches “gần cổng hơn” but does not explicitly prohibit exposing canvas coordinates or speculating about entrance location.
- The map panel is `AgentContextMap.tsx`; comparison state/hint is in `AgentPage.tsx`, with a bottom hint shown whenever exactly one option is selected.
- Backend already asks the composer to compare options and write 220–380 words, so the next inspection must determine whether grounded data is too sparse or prompt instructions allow shallow/raw-coordinate answers.
- `AgentContextMap` delays details by 720 ms and renders only four fields with 8–10 px typography; actions are 9 px. These sizes explain the readability issue.
- The odd comparison notice is a fixed-position `.agent-compare-hint` shown after exactly one selection; clicking it silently auto-selects the next recommendation rather than letting the user choose. It should be removed in favor of clear selection states and an inline comparison panel once two options are selected.
- The contextual map already has an explicit close button. Existing full-map navigation can remain, while directions should be a separate external action based on a real cemetery address or supported geographic coordinates—not internal canvas `mapX/mapY`.
- Backend `RecommendationOption` already contains full `plots`, including plot type, row/column and internal geometry; the frontend `AgentRecommendation` type omits that nested field even though persisted recommendation metadata likely carries it at runtime.
- The plot database/view also supports `description`, but the recommendation query does not currently select it. Enriching the grounded recommendation payload can support a more useful card and more detailed LLM analysis without extra client requests.
- The customer map page exposes richer plot information and should be used as the field/label reference rather than inventing new market claims.
- The full map displays row, status, price, area, size, direction, availability, live viewer/selector counts, description, and an internal “Tìm đường” guide. The contextual map should surface the stable useful subset and deep-link to this existing route feature.
- `GuidedTourMap` fetches `/plots/map`; its frontend model currently drops description, size, row, plot number and live counts from that response. Extending this model is the cleanest way to enrich the context card with authoritative map data.
- `/plots/map` already returns authoritative `rowCode`, `plotNumber`, `status`, `plotType`, and `description`, in addition to the four displayed fields.
- Opening the full map with a `highlight` query already selects the plot and turns on its internal route guide. A dedicated “Tìm đường” action can deep-link with explicit route intent while retaining “Bản đồ đầy đủ” as a separate action.
- The guided SVG renders plot highlights without plot-code text, so the earlier overlapping-label issue is already avoided in this component.
- The shared frontend map defines the main gate at `(460, 1560)` and secondary gate at `(1310, 1560)` in the same canvas coordinate system used for plot geometry. This makes a deterministic internal proximity calculation possible, but those raw coordinates must never be shown to customers.
- Current prompt examples themselves mention “farther from the entrance” and “services nearby” without requiring a grounded proximity/service relationship. This encourages the exact speculation seen in the screenshot and must be tightened.
- The composer serializes the complete tool result to the LLM and only says “never expose raw JSON or internal IDs”; it does not explicitly classify `mapX/mapY` as internal rendering geometry.
- The planner/DTO/tool schemas have no structured “near entrance” preference, so that request currently cannot influence ranking. The LLM can only see raw geometry afterward and guesses.
- A robust fix requires a `preferNearEntrance` requirement plus a deterministic proximity value derived from the shared map coordinate system, used for ranking and expressed as a customer-facing relative access label—not raw coordinates.
- The planning prompt still contains a stale statement that a deterministic scope guard handles unrelated messages, even though that guard was removed in the prior change; this should be corrected while updating the planner prompt.
- Recommendation scoring is currently based on budget, zone, direction, group/type/count only. Any entrance preference is ignored by both rule-based and external ranker ordering.
- The backend already returns nested plots in each recommendation, and the contextual map separately fetches authoritative map rows. We can add entrance-relative summaries to the recommendation while enriching the card from `/plots/map`.
- A useful price explanation can be grounded as “position within currently available matching inventory” (min/median/max/candidate count), but must not be called the broader market price without an external market dataset.
- The full-map highlight effect previously enabled route guidance unconditionally. It is now being separated so “Bản đồ đầy đủ” opens details while “Tìm đường” explicitly enables the existing internal route guide.
- `getCemeteryCoordinates` returns normalized row and plot number, and `ZONE_META` exposes plot type/size; the contextual card can enrich `/plots/map` rows without invented values.
- Live prompt-v9 smoke test returned 3 grounded recommendations with no raw coordinates and no request for the customer to locate the gate; it included price and entrance context.
- The same smoke test exposed a coordinate-system mismatch: DB `mapX/mapY` values (legacy/admin scale) do not match the customer map’s plot-code-derived layout. Entrance ranking must use the customer layout algorithm, not DB geometry.
- The second end-to-end LLM smoke timed out because configured OpenAI keys exhausted sequential 15-second timeouts before NVIDIA; backend logs confirm provider rotation rather than an application exception.
- The direct recommendation endpoint is healthy and now emits customer-map access summaries plus inventory context (72 matching available candidates), but returned Khu F ahead of available Khu H plots. The option-group generation/ranking truncation order needs inspection before declaring entrance ranking correct.
- Root cause of the remaining Khu F ordering was `buildOptionGroups` truncating the first 20 price-ordered candidates before entrance-aware ranking. Candidate grouping now orders by verified access first whenever `preferNearEntrance=true`.
- Final direct API verification now ranks H-02-005, H-02-004 and H-01-005 first; all three are labeled near Cổng chính on the customer map and remain under the 100 million VND budget.
